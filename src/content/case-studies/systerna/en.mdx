## Summary

Systerna is a dashboard for the usage, limits and costs of the developer services behind my projects. It answers one question first: what is about to run out, and when? The Overview puts the metrics that need attention on top, with their reason and their reset date, and every number says where it came from and how old it is.

It has collected real data since 4 November 2026 and is the screen I check each morning. On 19 November it tracked 36 metrics from eight sources, seven providers and my Raspberry Pi, 27 of them against a limit. It is private for now: it shows monthly forecasts only as preliminary until the first monthly reset on 1 December gives them something to be checked against, and it is not yet packaged for anyone else to run.

## What I owned

All of it: the question, the product and data rules, the design, the code and running it. It started as documentation on 29 October 2026, and the first code followed on 2 November, after a feasibility milestone had shown which providers could be read at all.

I wrote the specification, the milestones with their acceptance checks and a decision record for every significant choice, 37 by 17 November. I ran every probe against a provider myself, with tokens the coding agents never saw, and I approve each design in a canvas before it is built.

## Problem and constraints

My projects run on free tiers: Neon and Vercel for Kultomat, GitHub Actions, Cloudflare, Resend for email, Netlify, Oracle and Google Cloud's always-free machines and a Raspberry Pi at home. Each free tier has its own limits, its own reset day and its own dashboard. Some pause the whole service at 100 %. I found out about a limit when I hit it.

The constraints shaped everything:

- **No budget.** Systerna has to run on free tiers itself, and it watches its own usage like everything else.
- **Providers do not want to be read.** Several free plans show their quotas only in a dashboard. Vercel Hobby has no API for them at all; Neon's consumption API needs a paid plan. A key that can read usage can often do much more.
- **Honesty.** An unknown value must never look like a zero, an old value must always carry its date, and a provider's estimate must never be shown as its bill.

<Decision

## The build

Collection runs on a schedule kept apart from the hosting. A Cloudflare Worker and Vercel's cron wake the app; the app decides what is due for each metric, takes a lease so two runs never collide, and backs off when a provider says to wait. GitHub, Cloudflare and Neon are read from the server. Oracle and Google Cloud are read by Cloudflare Workers, and Resend, Netlify, the Pi's own health and TryPost by collectors on the Pi.

Every reading is stored with its source, time and quality. A failed collection keeps the last good value and says how old it is, and the rules for this live in tested domain code: unknown is never zero, stale data is always dated, reported and estimated money are never added together. Metrics whose provider reports them without promising billing accuracy, such as Neon's, are labelled experimental on their own page.

The interface is custom: Next.js with SCSS Modules and my own component kit, drawn from tokens in the approved design, on dark surfaces, with passkey sign-in. Alerts go in-app and by email. Each provider has its own colour and mark, so a row is recognisable before it is read.

## AI and collaboration

I worked with AI coding agents. I wrote the specification, the milestones and the decision records in the repository, and agents implemented them one pull request at a time, about 290 by 19 November 2026. Agents also prepared the feasibility research and the audits (security, architecture, correctness, performance, tests and CI, web quality), which I read and decided on.

The agents never held a provider key. Every probe in the feasibility milestone was a read-only request I ran myself, and the agents worked from the dated, redacted evidence I recorded.

Systerna itself calls no AI model. Its forecasts are plain arithmetic on the readings, with the method, the number of points and the confidence shown beside each one.

## What I would <Re>re</Re>think

I planned four integrations and assumed most providers would have an API for the numbers their dashboards show. Vercel's free plan has none, and Neon's needs a paid plan. I would check that before choosing a provider for a project, not after: the free tier I cannot watch is the one that surprises me.

I would also have planned for forecasts that cannot be proven yet. A monthly forecast needs a month of history before it can be checked, and waiting a month for any answer felt wrong when a quota was at 88 %. Preliminary forecasts, clearly labelled and kept out of the alerts, should have been in the plan from the start.

Some things wait on purpose. Web Push, a second alert channel independent of email, is required before anyone else relies on Systerna. A public version, Systerna as a free service or as a package anyone can run on their own machine, is written down as a direction, not started: its first step is a self-hostable release once the forecasts have met a real reset.
